# Rollback rehearsal: 0.4.0 to 0.3.0 and back

Date: 2026-09-28. Operator: the maintainer's release session, in a throwaway `HOME` with
`XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `CUBBY_STATE_DIR` and `CUBBY_CONFIG` unset. No service
manager was involved: the agent's unit is removed before a rollback (`docs/RUNBOOK.md`
section 4). The release session's script (not committed) ran the steps below; each new file was
created in the throwaway Downloads folder, dated two hours back, before its step.

Builds: 0.3.0 from tag `v0.3.0`, 0.4.0 from `release/0.4.0`, each in its own venv.

| Step | Command | Result |
|---|---|---|
| 1 | 0.4 `cubby init`, then `cubby run` on a text invoice, a PNG and a broken PDF | rc 0, 3 moved, a warning for the broken PDF (`pdftotext: exit: status 1`) |
| 2 | 0.3 `cubby history`, `cubby status` on 0.4's state | rc 0, the 0.4 run listed |
| 3 | 0.3 `cubby run` with the config 0.4 wrote, on a new PNG | rc 0, 1 moved |
| 4 | 0.3 `cubby undo`, then `cubby undo --run` the 0.4 run | rc 0, 1 then 3 files restored |
| 5 | 0.4 `cubby history`, `status`, then `run` on the four files the undos of step 4 put back plus a new PNG, and `undo`, then `doctor` | rc 0, both earlier runs shown undone, 5 moved and restored |
| 6 | 0.4 `status --json` over a ledger holding 0.3 and 0.4 records | `activity.extraction_failures` 2 (the 0.3 record reads as 0) |

Finding: no incompatibility in the config, the journal or the ledger in either direction.
`cubby install --help` lists the same flags in both versions. What a rollback gives up comes
from the 0.4 changelog and the code, not from this rehearsal: 0.3's agent is not given
`--no-content`, shows file names raw, and on macOS logs to its state folder (#27);
`docs/RUNBOOK.md` section 4 lists them. Not rehearsed: a real launchd or systemd unit, and a
real Mac.

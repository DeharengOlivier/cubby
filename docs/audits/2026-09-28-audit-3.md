# Audit 3: cubby (level L2) at b6dd32b (2026-09-28), release v0.3.0

Standards: `CODING-RULES.md` and `SECURITY-CHECKLIST.md`, version 2026-09-25.1 (scorecard view
`coding-standards/references/scorecard.md`, same version).
Method: `/audit-code` procedure on a fresh clone of `main` at b6dd32b501aa (tag v0.3.0,
committed 2026-09-28 10:52 +0200, 207 commits, merged through PR #19), `uv sync --locked
--all-extras`, the project's own checks, black-box CLI probes in a throwaway HOME, an
independent rebuild of the published v0.3.0 artifacts, and read-only `gh` queries.
Previous: [audit 1](2026-09-28-audit-1.md) 5.7/10, [audit 2](2026-09-28-audit-2.md) 8.2/10,
both with the gate BLOCKED.

Cubby is a local CLI and per-user agent (launchd or systemd `--user`) that moves the files of
one folder into category subfolders, reversibly, with no network, no accounts and no data of
its own beyond an undo journal, a run ledger and a log. Since v0.2.0, thirteen pull requests
(#7 to #19, +8 941/-1 199 lines) closed most of audit 2's plan: the CLI is a package under the
complexity budget, an AST test holds subprocess timeouts, every log line carries the run id
and version, `--json` outputs have published schemas checked against real output, capacity is
measured to 200 000 files, the runbook was executed by two first-time operators, the rollback
to 0.2 was rehearsed, and the release rebuilds byte for byte (I verified it). The code is in
very good shape. The most important thing to fix is small and new: untrusted file names reach
the terminal unescaped, so a file whose name holds escape sequences can clear the screen and
forge what `plan`, `run`, `undo` and `status` print. The gate stays blocked on the unconfirmed
2FA, as in the last two audits.

## Release blockers (applicable P0 failed or not verified; distinguish the two)

FAIL:
1. **SEC-08-004** (output encoding appropriate to the context), applied to the terminal
   context. File names are untrusted input (`docs/THREAT-MODEL.md`, SEC-01-006), and they are
   written raw to stdout by the text renderers. Measured: a file named `evil\e[2J\e[31mFAKE.pdf`
   in the watched folder makes `cubby plan` emit the bytes `033 [ 2 J 033 [ 3 1 m` (`od -c` of
   the output). A name with a newline breaks the layout of `plan`, `run`, `undo` ("restored
   ...") and the "recent log" lines of `cubby status`. The only stdout treatment is
   `errors="backslashreplace"` for undecodable names (`src/cubby/cli/main.py:163-173`). The JSON
   outputs and the JSON log are correctly escaped (`\u001b`).
   -> a file planted in Downloads (an extracted archive, a sync tool, another local process;
   browsers usually strip control characters from download names) can clear the screen and
   print a forged report, for example hiding a move or faking "Restored N file(s)". Severity
   low (local, needs a crafted name, no code execution shown), but the register marks
   SEC-08-004 N/A with the reason "no HTML or templates", and that reason does not hold: an
   interpreting output context exists. The same names also reach the `notify-send` body,
   which many notification daemons parse as markup. That part is unmeasured (no `notify-send`
   on this host) and is listed under Not verified.
   Classification note: the control's wording names web contexts only. I read the terminal as
   the same family ("data being interpreted as instructions", section 8). If the maintainer
   reads it as web-only, the row is still an unjustified N/A and needs a decision. See the
   standards feedback.

NOT_VERIFIED:
2. **SEC-14-003** (MFA on every account with access): one account (collaborators: the owner
   only). `gh api user --jq .two_factor_authentication` returns nothing with this token. The
   maintainer has not confirmed 2FA.

Gate: **BLOCKED** (1 FAIL, 1 NOT_VERIFIED). No other applicable P0 failure found within the
scope checked below.

## Not verified

- **SEC-14-003**: 2FA on the maintainer's GitHub account. The token cannot read the flag, and the maintainer has not confirmed it.
- **Notification delivery and markup**: no `notify-send` or desktop session on this host, and the Mac is not reachable. Whether a file name with `<b>` or `<a href>` renders as markup in a real notification was not measured.
- **macOS in a real login session**: launchd install, `textutil`, `osascript`. CI runs the macOS unit and E2E tests, but no launchd.
- **Direct push refusal**: read from the protection settings, not attempted (read-only audit).
- **Classification accuracy on a real Downloads folder**: no labelled dataset.
- **Dependency freshness beyond advisories**: `pip-audit` is clean. Outdated-but-safe versions were not listed (Dependabot is relied on).
- **Origin of `~/.local/state/cubby/cubby.lock` on this host**: an empty lock file dated 2026-09-28 05:31, before this audit. My runs did not change it (mtime unchanged after the suite). The suite as it stands at b6dd32b wrote nothing into an empty `HOME` (measured), so I do not attribute it to the current tests. It may date from an earlier commit (`tests/test_isolation.py` records such a leak once) or from a drill.
- **The exploratory session report and the reviews of #13 to #18**: not found. Only their resolutions were available.

## Remediation plan (impact / effort)

1. [1h, high] Route every human-readable rendering of a file name (plan, run, undo, explain,
   history, `status` recent log, `log` text mode, error lines) through one `shown(name)`
   helper that escapes C0 and C1 control characters, DEL and bidi overrides (for example as
   `\x1b`, `\n`, `‮`). Add a Hypothesis test over the full alphabet asserting that no
   control byte reaches stdout or stderr. Escape `<`, `>` and `&` in the `notify-send` body.
   Add the output contexts to `docs/THREAT-MODEL.md` SEC-01-006 and set SEC-08-004 to PASS
   with that test as evidence.
   -> SEC-08-004 FAIL -> PASS; Input domain 4 -> 5; Security testing 4 -> 5; USE-01 8 -> 9.
   Evidence that raises it: the property test in CI, plus `cubby plan | od -c` on a planted
   `\e[2J` name showing `\x1b` in the output.
2. [user, 1 min] The maintainer confirms 2FA in GitHub settings, or runs `gh auth refresh -s user`
   and `gh api user -q .two_factor_authentication` and records the answer and date in the register.
   -> SEC-14-003 NOT_VERIFIED -> PASS. With item 1, this unblocks the gate.
3. [user, 5 min] Run `cubby doctor --notify` on the Mac and on a Linux desktop, and record
   that the notification was seen (screenshot or dated note in the register).
   -> OBS-03 7 -> 9; SEC-18-007/008 NOT_VERIFIED -> PASS; Logging domain 3 -> 4.
4. [30m, high] Post the reviewer's own text on every PR, not only its resolution. Backfill #13
   to #18 (the review files, for example `pr15-review.md`, pasted or linked). Add a step to
   the PR template or a small required check that a comment headed "Independent review
   record" exists before merge. Correct the register row.
   -> PRC-02 7 -> 9; PRC-06 7 -> 9 (together with the SEC-08-004 row from item 1).
5. [30m, med] Log each extraction backend failure (timeout, non-zero exit, parser exception)
   at WARNING with the run id and the backend name, and count such failures per pass in the
   ledger. Keep the graceful fallback.
   -> REL-07 8 -> 9; OBS-01 8 -> 9. Evidence: a test with a timing-out fake converter asserting
   the log line and the ledger count.
6. [1h, med] Measure the flaky rate: a script over `gh run list` and `gh run view --json jobs`
   that counts jobs failing and then passing on the same SHA, with a budget written in the
   register and checked at each release.
   -> TST-05 8 -> 9.
7. [2h, med] Keep counts instead of outcome objects in `watch` mode, or stream them, and
   measure a pass at 400 000 files to reach the memory breaking point instead of extrapolating it.
   -> PRF-04 8 -> 9; SCL-02 8 -> 9.
8. [ongoing, low] Keep PRs under about 600 lines and to one purpose, and return to one commit
   message convention.
   -> PRC-03 7 -> 8.
9. [org, low] A second person with commit rights who has made and released one change.
   -> PRC-05 5 -> 8.
